# 莞工学工系统 · 自动考勤

莞工学工系统（[stu.dgut.edu.cn](https://stu.dgut.edu.cn/)）勤工助学岗位的自动打卡工具，适用于学生助理、助理班主任等职位的日常考勤：**该签到的时候自动签到，该签退的时候自动签退，避免"忘记打卡"和"打了卡忘记签退"。**

> 本仓库基于 [Bertramoon/DGUT-Auto-Attendance](https://github.com/Bertramoon/DGUT-Auto-Attendance)
> 重写。原版依赖的第三方库和页面路径在 2022 年之后就已全部失效，**2026 年直接使用原版是无法打卡的**，
> 具体原因见 [第 2 节](#2-为什么原版失效了)。

---

# 1. 项目概述

## 1.1. 工作原理

程序采取 **对账（reconciliation）** 的思路，而不是"到点触发一次"：

```
每轮循环：
  1. 算出「此刻我应该在岗吗？」        ← 来自 schedule.json / special.json
  2. 读服务端真实状态                  ← 学工系统上「上岗考勤」页面
  3. 不一致才发动作（签到 / 签退）
  4. 动作之后再读一次页面，确认真的生效
```

这样做的好处是 **幂等 + 自愈**：

- GitHub Actions 排队、延迟或漏跑后，恢复运行会再次读取真实状态并收尾；
- 同一个时刻重复运行也不会重复打卡；
- 每一次动作都有服务端返回的状态作为证据，不会出现"日志说成功、实际没打上"。

## 1.2. 运行方式

GitHub Actions 单个托管 job 最长只能跑 360 分钟，而一天的考勤时段横跨 08:30–21:00，
需要多次运行接力。当前工作流 **每 15 分钟提供一次初次启动和故障恢复机会**
（`cron: '7,22,37,52 * * * *'`），保留 `concurrency` 组并设置
`cancel-in-progress: false`：后来的运行等待，不中断正在守着签退时刻的进程。
同组默认只保留一个等待中的运行，新的定时运行会替换旧的等待项。

**日间接力会主动创建下一轮，不再等待下一次 cron。** 本轮开始考勤前，
`workflow_relay.py` 检查当天是否还有未结束的排班；若有，使用 GitHub 自动提供的
`GITHUB_TOKEN` 派发一个 `workflow_dispatch` 运行，由同一并发组等待本轮结束。
上午 12:00 签退后，这个已排好的运行接手并等到下午 14:30 签到。
当天全部班次结束后停止派发，避免夜间无排班时不断启动空任务。
无需增加个人令牌；工作流已设置 `actions: write` 权限。
派发失败不会阻止本轮考勤，但结束后会将接力失败标红。

工作流传入 `--finish-window`，每次完成启动时的当前班次或下一班次，
**确认服务端已经签退后退出**，再让等待中的运行接手。这样避免上午启动的进程
一直跑到下午班次中途才到达运行上限，也避免每小时强制取消打断正在进行的请求。
对账失败后每 30 秒重试；班次结束后留出 600 秒收尾，持续失败会使 Actions 显示失败，
不会用一条“程序结束”掩盖未确认的签退。
600 秒是收尾重试窗口；窗口结束时正在执行的请求仍受网络超时控制，可能稍后才返回。
无法确认归属的在岗记录会保留，并报告收尾未确认，供人工核对。

单个进程有两道闸：

- 软上限 `--max-hours 5.5`：到点后如果当前时段马上就要结束，会延长一小会儿
  把签退做完再退出；
- 硬上限 `--hard-max-hours 5.8`（必须小于 workflow 的 `timeout-minutes: 358`）：
  绝不允许超过这个时间还在跑，来不及收尾就留给下一轮接力。

**这些措施无法保证托管运行器始终在线或严格准点。** GitHub 的定时事件可能延迟，
负载过高时甚至丢弃；运行器失联时，代码也无法在已经失联的机器上继续签退，
等待中的运行要等旧任务被 GitHub 判定失败或超时后才能接手。
恢复时可以结束遗留记录，但学校系统记下的是实际恢复时的签退时间，
程序不能把已经漏掉的历史签退时间改回 12:00 或 17:00。
若岗位要求准点签退，建议在持续在线的电脑或服务器上常驻运行，并配置进程自动重启。
参见 [GitHub 定时事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
和 [并发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

## 1.3. 桌面版：双击就能跑（推荐）

不想碰命令行的话，用桌面版：

1. 双击仓库里的 **`启动打卡助手.bat`**；
2. 第一次运行会自动装依赖（约 1–2 分钟），之后直接弹出窗口；
3. 填学号密码，勾上「记住账号」，以后就不用再填；
4. 想全自动就点 **▶ 开始自动打卡**，窗口可以最小化，它会按 `schedule.json` 自己签到签退。

窗口上的按钮：

| 按钮 | 作用 |
| --- | --- |
| 查看状态 | 只读一次服务端状态，**不产生任何考勤记录** |
| 立即签到 / 立即签退 | 手动补一次；已经在岗（或本来不在岗）时不会重复动作 |
| ▶ 开始自动打卡 | 按排班表自动签到签退，日志实时显示在窗口里 |
| ■ 停止 | 结束自动打卡 |
| **编辑考勤时间表…** | 直接在窗口里改每周排班，不用手编 JSON |
| **退出程序时若在岗则自动签退** | 勾选后（默认勾选），关窗口前会检查一次：还在岗就立刻签退 |
| 创建桌面快捷方式 | 在桌面放一个图标，以后双击图标就能打开 |

### 编辑考勤时间表

点「编辑考勤时间表…」会打开一个小窗口，按周一到周日逐天列出考勤时段：

- 时间是 `时:分` 格式，`8:30` 和 `08:30` 都认，全角冒号也认，保存时会统一成 `08:30`；
- 某一天**不加任何时段 = 当天不考勤**；
- 有「把周一时段复制到周二~周五」的快捷按钮；
- 保存会写回 `schedule.json`，**云端 Actions 和桌面版共用同一份**；
- 格式错误（比如 `25:00`、结束早于开始）会当场拦下并告诉你哪一天的哪一段有问题。

> 注意：自动打卡**运行中**改排班，新的时间表要下次点「开始自动打卡」才生效。

### 关闭窗口时会自动签退

关窗口前程序会：
1. 先让正在跑的自动打卡线程停下来；
2. 登录并读一次服务端状态；
3. **如果还在岗，立即签退**，然后才真正关窗。

如果签退失败或网络太慢（超过 90 秒），会弹出提示让你自己确认是否仍在岗，
而不是默默关掉留下一个挂着的会话。不想要这个行为就去掉那个勾。

桌面版**复用同一套对账循环**，所以和云端版行为完全一致（幂等、可自愈）。
账号只保存在本机的 `account.ini`，该文件已被 `.gitignore` 忽略，**不会上传到 GitHub**。

> 前提：电脑上装了 Python 3.10+ 并勾选了 "Add python.exe to PATH"。
> 没装的话 `.bat` 会提示下载地址。

# 2. 为什么原版失效了

原版 `attendance.py` 依赖 PyPI 上的 `dgut-requests`（**最后发布于 2022-10-04**），它有两个致命问题：

## 2.1. 登录其实从未成功

`dgut-requests` 的 `login()` 在向中央认证（CAS）提交时 **没有携带 `service` 参数**，
于是 CAS 把登录票据发给了默认服务，而不是学工系统。

随后它去访问学工系统时，服务器返回的 body 只有 152 字节的一段 **JavaScript 跳转**：

```html
<script>window.location.href='https://auth.dgut.edu.cn/authserver/login?service=...'</script>
```

`requests` 不会执行 JS，所以会话自始至终都没有建立起来。
但库内部却无条件把 `is_authenticated` 置为 `True`，于是所有后续请求都静默失败。

## 2.2. 无论成败都报告"签到成功"

原库的 `attendance()` 方法拿到响应后 **不做任何校验**，直接返回 `"签到成功"`。
所以日志里永远是成功，实际可能什么都没发生。

## 2.3. 页面路径和表单都变了

| 项目 | 2022 原版 | 现在（2026） |
|---|---|---|
| 勤工助学模块 | `/student/partwork/` | `/student/partWorkNew/` |
| 考勤页面 | `attendance.jsp` | `attendancePre.jsp` |
| 表单字段 | 单个 `session_token` | **同名 `session_token` 出现两次** |

> 关于 `session_token`：页面上有两个同名的隐藏字段，浏览器会把两个都提交。
> 用 `requests` 时如果用 `dict` 传参会丢掉一个，必须传 `list[tuple]`。
> 这一点在 `attendance.py` 的 `_payload()` 里已经处理。

## 2.4. 本仓库的做法

- **不再依赖 `dgut-requests`**，登录逻辑重写在 `dgut_client.py` 里：
  CAS 提交时直接带上 `service=https://stu.dgut.edu.cn/`，一次拿到有效会话；
- 登录页解析改为 **逐个 `<input>` 解析**，而不是原库那种"一条按固定顺序跨 6 个字段的大正则"
  （页面只要稍微重排，那种正则就会静默匹配失败）；
- 每次动作之后 **重新读取页面确认状态**，没生效就抛异常。

# 3. 部署

## 3.1. fork 仓库

![fork仓库](https://gitee.com/bertramoon/img/raw/master/Auto_Attendance/Fork%20repository.png "")

## 3.2. 设置 Secrets

仓库 **Settings → Secrets and variables → Actions**，添加：

| Secret 名称 | 含义 | 必填 | 示例 |
|---|---|:---:|---|
| `USERNAME` | 中央认证账号（学号） | ✅ | `20xxxxxxxxx` |
| `PASSWORD` | 中央认证密码 | ✅ | `********` |
| `SERVER_KEY` | Server酱 SendKey（微信推送通知） | ❌ | `SCT123456...` |

> `SERVER_KEY` 只填 **SendKey 本身** 即可（例如 `SCT123456...`）。
> 为兼容旧配置，填成 `-K SCT123456...` 这种写法程序也能识别。

## 3.3. 设置考勤时间（`schedule.json`）

**不需要改 Python 代码**，只改 `schedule.json`：

- key `"0"`–`"6"` 表示 **星期日 – 星期六**（每周第一天是星期日）；
- value 是一个列表，每个元素是 `["开始时间", "结束时间"]`；
- 时间必须严格写成 `"时:分"`（`"8:30"` 可以，`"8:3"`、`"8:30:00"` 不行）；
- 空列表 `[]` 表示当天不考勤。

```json
{
    "0": [],
    "1": [["8:30", "12:00"], ["14:30", "16:00"]],
    "2": [["8:30", "12:00"]],
    "3": [],
    "4": [["8:30", "10:10"]],
    "5": [["10:25", "12:00"]],
    "6": []
}
```

上表含义：周日、周三、周六不考勤；周一是 `8:30-12:00` 和 `14:30-16:00` 两段；
以此类推。

> 上面只是**格式示例**。本仓库当前实际使用的时间表是**每天**（周日到周六都一样）
> 三段：`08:30-12:00`、`14:30-17:00`、`18:00-21:00`。
> 想改的话，桌面版点「编辑考勤时间表…」最省事。

## 3.4. 某一天特殊安排（`special.json`）

需要单独调整**某一天**时用这个文件，格式是 `"年-月-日": [[开始, 结束]]`。
**只要某天出现在这个文件里，就以它为准**，同时也会忽略"节假日不打卡"的判断。

```json
{
    "2026-10-01": [],
    "2026-10-08": [["9:00", "11:30"]]
}
```

- `"2026-10-01": []` → 这天不打卡（国庆）；
- `"2026-10-08": [["9:00", "11:30"]]` → 这天改在 9:00–11:30 打卡。

## 3.5. 配置 `config.ini`

```ini
[attendance]
holiday_attendance = True
workAssignmentId = 38605
```

- **`holiday_attendance`**：`True` = 法定节假日也照常打卡；`False` = 跳过节假日。
- **`workAssignmentId`**：考勤职位的 ID。只有一个职位时可以留空（自动取第一个）；
  有多个职位时必须指定，否则会打错岗位。

> 查看自己的 `workAssignmentId`：登录学工系统 → **勤工助学 → 上岗考勤**，
> 页面上的"工作考勤"下拉框里，`<option value="38605">计算机学院学生工作助理</option>`
> 中的数字就是它。本仓库已按当前账号填好（`38605`）。

## 3.6. 开启 Actions

仓库 **Actions** 页面 → 启用 workflow。
工作流也可以 **手动触发**（`workflow_dispatch`），方便测试。

# 4. 本地运行与测试

```bash
pip install -r requirements.txt

# 只看状态，不打卡
python dgut_client.py state -U <学号> -P <密码>

# 手动签到 / 签退
python dgut_client.py in  -U <学号> -P <密码>
python dgut_client.py out -U <学号> -P <密码>

# 完整跑一遍主程序（--dry-run 只报告、不真的打卡）
python attendance.py -U <学号> -P <密码> --dry-run --once
python attendance.py -U <学号> -P <密码> --once

# 完成当前或下一班次并确认签退后退出（云端工作流使用此模式）
python attendance.py -U <学号> -P <密码> --finish-window --retry-interval 30 --cleanup-seconds 600
```

也可以把账号放在环境变量里，避免出现在命令行历史中：

```bash
export DGUT_USERNAME=20xxxxxxxxx
export DGUT_PASSWORD=********
python dgut_client.py state
```

## 常用参数

| 参数 | 说明 |
|---|---|
| `--once` | 只做一轮对账就退出（适合手动测试、或高频 cron） |
| `--dry-run` | 只打印"将要做什么"，不真正打卡 |
| `--interval` | 对账间隔秒数，默认 `600`；到达考勤时刻会提前唤醒 |
| `--retry-interval` | 对账失败后的重试间隔秒数；云端设为 `30` |
| `--cleanup-seconds` | 最后签退或本次目标班次结束后的收尾时间；云端设为 `600`，仍失败则返回非零退出码 |
| `--finish-window` | 完成启动时当前或下一班次，确认签退后退出，让下一次云端运行接手 |
| `--max-hours` | 单次运行最长小时数（软上限），默认 `5.5`（Actions 上限 6 小时） |
| `--hard-max-hours` | 单次运行绝对上限，默认 `5.8`；到点无论如何都退出，只剩下一轮接力 |
| `--schedule` / `--special` / `--config` | 指定配置文件路径 |
| `-W` | 指定 `workAssignmentId`，优先级高于 `config.ini` |

```
      main.yml          GitHub Actions 工作流
```

# 6. 常见问题

## 6.1. 设置了 8:30 打卡，为什么工作流提前启动了？

当前工作流每 15 分钟提供一次启动机会，启动后由程序自己等待到考勤时刻再打卡。
GitHub Actions 的定时事件可能延迟或丢弃，因此 cron 时间不是实际启动时间的保证。
在时段中途才恢复时，程序会读取真实状态并按当前时间对账，但不能补回已经过去的签到、签退时间。

## 6.2. 会不会泄露我的账号密码？

不会，两条路都不进仓库：

- **云端版**：账号密码存在 GitHub Actions Secrets 里，由 GitHub 保管，不会出现在仓库文件或日志里；
- **桌面版**：存在本机的 `account.ini`，该文件已在 `.gitignore` 中忽略，
  `git status` 里根本不会出现它。

## 6.3. 打卡时段中途程序退出了，会不会一直留在"在岗"状态？

服务端不会因为本地进程退出而自动签退。下次成功运行时会检查遗留记录：

- 若这条"在岗"记录属于**已经结束的班次或更早的日期**，程序会先签退；
  即使恢复时已经进入下一班次，也会先确认旧记录结束，再决定是否签到；
- 若都不满足（例如用户在非考勤时段自己手动签了到），程序会 **保持原样并打印原因**，
  不会贸然替你签退，以免破坏真实工时。

恢复时的签退只能记录实际恢复时间；停机期间漏掉的历史边界需要人工核对考勤。

## 6.4. 学校又改版了怎么办？

页面结构变化时，程序会抛出 `PageChangedError` 或 `DgutError` 并在日志里说明具体哪个字段没找到，
而不是像原版那样静默地"假装成功"。看到这类报错就说明该更新解析逻辑了。

另外，如果登录页**确实**变了（而不是上一次修复前的"自己把自己卡住"），
现在的报错会带上跳转后的地址和响应字节数，方便一眼看出到底是学校改版还是会话状态不对。

## 6.5. 节假日到底打不打卡？

由 `config.ini` 里的 `holiday_attendance` 决定：

- `True`：**每天都按排班表打**，法定节假日照打（本仓库当前是这个值，适合"节假日也要值班"的岗位）；
- `False`：先用 `chinesecalendar` 判断，是法定休息日就整天不打卡。

不管这个值是什么，**只要某一天写进了 `special.json`，就以 `special.json` 为准**：

```json
{ "2026-10-01": [] }
```

空列表的意思是 **这天不考勤**，程序会明确跳过，不会退回星期表去打卡。

## 6.6. 桌面版的窗口一闪就没了怎么办？

说明启动时崩了。崩溃信息会写进同目录的 `crash.log`，同时弹出提示框；
也可以直接在命令行里跑 `python gui.py`，这样错误会完整打印出来。

## 2026-10-09 修复"工时被合并成一条"和"多出一条假记录"

10-08 的考勤明细里出现了两条异常记录：`12:00:13 ~ 12:10:12`（0.17 小时）和
`14:30:04 ~ 21:00:03`（6.50 小时），当天因此被判"考勤需确认"。
对着 Actions 日志逐条核对后，定位到三个独立的问题：

- **登录会把自己卡死（最严重，也是 17:00 没人签退的真正原因）。**
  会话里还留着中央认证的 cookie 时，再请求登录页会被 302 直接送回业务系统，
  拿到的页面自然没有 `pwdEncryptSalt`，旧代码于是抛"登录页结构已变化"。
  更糟的是它同时把 `logged_in` 置为 `False`，此后**每一轮都重试这条走不通的路**：
  10-08 从 15:00 到 16:21 整整瞎了 80 分钟，两个进程先后放弃，
  14:30 签到的记录于是一直挂到 21:00 才被下一次运行签退。
  实测：同一会话再取登录页 → 跳转 2 次、61770 字节、无 `pwdEncryptSalt`；
  清空 cookie 再取 → 0 次跳转、19251 字节、字段齐全。
  现在 `login()` 取表单前先 `session.cookies.clear()`，失败重试一次，
  报错信息里还会带上跳转地址和字节数。
- **动作前用的是过期的时间判定（TOCTOU）。**
  11:59:33 这一轮判定"应该签到"，读完服务端状态已经跨过 12:00（约 38 秒），
  旧代码照样把签到发了出去 —— 12:00:13 那条 10 分钟的假记录就是这么来的。
  现在真正动作前会重新取一次北京时间，一旦跨过时段边界就放弃本轮，下一轮重新判断。
- **两次运行撞车，互相签退。**
  旧工作流有 4 个 cron 且没有 `concurrency`，10-08 当天确实有两个 job 在同时跑，
  一个在 12:00:05 签退、另一个在 12:10:13 又签退一次。
  当时改成每小时一次 + `concurrency` 主动取消旧运行，同一时刻只留一个进程。
  这不能保证新进程已经就绪，2026-10-12 已替换为等待旧运行完成班次后接手。

顺带修掉的其它问题：

- 进程跨午夜不会重新读排班（桌面版整夜开着时用的是前一天的 `schedule.json`）；
- 到达运行上限时若正在岗会直接丢弃会话，导致 17:00 无人签退；
  当时加入硬上限内延长收尾和后续运行接力，但接力仍受调度延迟、运行器故障影响；
- 新增 `tests/test_attendance.py`（19 个用例），
  其中包含上面两个 TOCTOU 场景的回归测试和工作流配置的断言。

改动文件：`attendance.py`、`dgut_client.py`、`gui.py`、
`.github/workflows/main.yml`、`tests/test_attendance.py`。

## 2026-09-29 修复线上问题

线上跑了几天后，从 Actions 日志和考勤记录里定位到三个会**把工时算错**的问题：

- **网络抖动会让整个进程崩掉，会话留在服务端没人签退。**
  `attendance.py` 的循环原来只捕获 `DgutError`，而 `requests` 的 `ReadTimeout`
  不属于它。9-29 那次就是这样：10:40:36 签到成功，11:31:21 一次读超时 → 进程崩溃 →
  这条会话一直挂到 17:27，**凭空多算 6.79 小时**。
  现在：客户端所有请求都走带重试的 `_request()`（3 次、递增退避，网络异常统一转成
  `DgutError`），主循环也改成捕获 `Exception`，单轮失败只记日志、下一轮照常重试。
  登录失败还会整体重试 3 次，不再让一次抖动废掉整个时间窗。
- **到达运行时长上限时如果正在岗，会话同样被丢下。**
  原来 `deadline` 一到直接 `break`。现在如果当前时段的结束就在 20 分钟内，
  会延长运行把签退做完；否则明确打一条警告，说明会话留待下一次运行收尾。
- **定时任务被 GitHub 排队拖得太晚，下午那个时段其实没人覆盖。**
  实测目标 07:30 的实际 09:40~10:40 才跑，目标 13:30 的更拖到 18:00~19:53。
  现在改成四个 cron（06:00 / 07:30 / 12:00 / 17:30 北京），每个时段都有备份。
  （10-09 曾改成每小时一次 + `concurrency` 主动取消接管；10-12 已改为每 15 分钟排队接力。）
